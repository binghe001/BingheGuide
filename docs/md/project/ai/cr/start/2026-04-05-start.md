## 一、项目背景

在这个代码质量下降、Bug满天飞的时代，谁还没犯过几次低级错误呢？特别是当你提交了一大坨代码，Review 完才发现有两个变量名起得一模一样，结果导致了一个凌晨三点把你从睡梦中叫醒的线上事故...

为了拯救这些在代码里迷失的灵魂，也为了给自己写代码找一个靠谱的"审稿人"，开始设计和开发这个智能代码审查系统。这是一个基于 AI 的代码审查工具，不仅能帮你找出代码里的奇葩，还能帮你评估代码质量，最后还能给你整一个精美的审查报告。

这个项目就像是代码界的"纠错老师"，每天兢兢业业地守在你的代码仓库里，用 AI 的智慧帮你把那些隐藏在代码深处的 Bug、代码坏味道和质量问题统统揪出来。

这个项目不是一个简单的Code Review项目，而是一个是一个基于AI大模型的智能代码审查系统，内置支持多种AI大模型，例如：deepseek、千问、智谱、openai等等，也可以快速扩展定义其他AI大模型。

## 三、项目亮点

### 3.1 技术亮点

**分层架构清晰**

- 接口层、多个AI大模型对接、代码平台（Github、Gitee、Gitlab）对接、推送平台（钉钉、微信、飞书）对接职责分离
- 职责明确，易于维护和扩展
- 符合单一职责原则和依赖倒置原则

**设计模式应用**

- **策略模式**：不同 Git 平台和消息渠道的策略实现
- **工厂模式**：动态创建 LLM 客户端
- **模板方法模式**：代码审查提示词模板
- **模板方法**：异步处理 Webhook 事件

**多语言支持**

- 自动检测代码语言
- 针对不同语言定制提示词
- 支持常见的编程语言

**多平台支持**

- GitHub、GitLab、Gitea 三大平台
- 统一的接口设计，易于扩展新平台

**多模型支持**

- OpenAI、DeepSeek、阿里云通义千问、智谱GLM等
- 通过配置切换，灵活适配

**多种通知渠道**

- 钉钉、企业微信、飞书、自定义 Webhook
- 灵活的配置方式

**数据统计功能**

- 代码质量评分
- 作者贡献统计
- 项目提交统计

**异步处理**

- Webhook 事件异步处理
- 不阻塞 HTTP 响应
- 提高系统并发能力

### 3.2 业务亮点

**自动代码审查**

- PR/MR 创建时自动触发审查
- Push 时可选触发审查
- 自动发布审查结果到代码平台

**客观评分**

- AI 自动计算代码质量分数
- 直观展示代码质量水平

**实时通知**

- 审查结果自动通知团队成员
- 错误信息及时通知运维人员

**历史记录**

- 审查日志持久化存储

## 六、技术选型

### 6.1 为何选 Spring Boot 3.2.5 + Java 17？

首先，Spring Boot 简化配置，开箱即用，就像快餐界的麦当劳，能让你快速填饱肚子（完成功能）。Java 17 呢，虽然是 LTS（长期支持）版本，但已经是现代 Java 的标准了，新的语言特性（比如 Records、Text Blocks、Pattern Matching）能让你写出更优雅的代码。

### 6.2 为何选 JPA 而不是 MyBatis？

JPA 像是在用 ORM 的"上帝模式"，你只需要定义实体类，剩下的映射、SQL 生成全自动搞定。MyBatis 像是"手动挡"，需要手写 SQL，适合对 SQL 有特殊要求的场景。对于这个项目，JPA 的自动映射和懒加载机制更符合我们"少写代码多睡觉"的原则。

### 6.3 为何选 SQLite 而不是 MySQL？

SQLite 轻量级、零配置，就像租房界的"合租室友"，刚开始一个人住（开发环境），部署的时候直接打包走人（生产环境）。MySQL 适合高并发场景，但成本高、配置复杂，就像租了一个豪华公寓。本项目默认用 SQLite，你也可以一键切换到 MySQL。

### 6.4 为何选 OkHttp 而不是 RestTemplate？

OkHttp 更现代、性能更好、连接池更智能，就像汽车界的"特斯拉"，自动化程度高，还能自动处理一些奇葩网络情况。RestTemplate 像是传统的燃油车，还能开，但不如电动的省心。

### 6.5 为何支持多种大模型？

俗话说"一千个读者眼中有一千个哈姆雷特"，同样代码的 AI 审查，不同大模型可能有不同见解。DeepSeek 性价比高，OpenAI 质量稳，阿里云通义千问国产化，满足不同场景需求。就像餐厅提供"川菜、粤菜、湘菜"三种选择，总有一款适合你的口味。

### 6.6 为何支持多个 Git 平台？

GitHub 众所周知，GitLab 企业常用，Gitea 自建首选。就像网吧提供"腾讯、百度、谷歌"三种上网方式，总有一个能连上网。

### 7.1 架构分层说明

#### 前端层
- **FrontendController**：提供简单的 HTML 页面，展示审查日志和统计数据
- **ReviewApiController**：提供 REST API，前端或第三方应用可以调用这些接口获取审查记录和统计信息

#### 控制器层
- **WebhookController**：接收来自 GitHub、GitLab、Gitea 的 Webhook 请求，是整个系统的入口
- **ReviewApiController**：提供审查日志查询 API

#### 服务层
- **CodeReviewService**：核心代码审查逻辑，包括语言检测、提示词加载、AI 调用
- **ReviewService**：管理审查日志的增删改查
- **ReportService**：生成各种统计报告

#### 数据访问层
- **Repository**：使用 Spring Data JPA，自动实现 CRUD 操作和复杂查询

#### 消息通知层
- **NotificationService**：统一的消息通知接口
- **DingTalkNotifier**、**WeComNotifier**、**FeishuNotifier**、**ExtraWebhookNotifier**：具体的实现

#### LLM 客户端层
- **LLMClient**：统一的大模型调用接口
- **LLMFactory**：根据配置动态创建客户端
- **OpenAIClient**、**DeepSeekClient**、**QwenClient**：具体的实现

## 十、技术难点与解决方案

### 难点 1: 代码语言自动检测

**问题**：如何从 diff 文件中准确判断代码语言？

**解决方案**：
1. 通过文件扩展名检测（最准确）
2. 从 diff 内容中检测特定语法特征（如 Vue3 的 `<script setup>`）
3. 统计语言出现频率，返回频率最高的语言

### 难点 2: 大模型 API 限制

**问题**：代码 diff 过长会超过大模型的 Token 限制。

**解决方案**：
1. 实现简单的 Token 估算（1 token ≈ 4 chars）
2. 超过限制时截断代码
3. 截断后重新检测语言

### 难点 3: Webhook 安全性

**问题**：如何防止恶意请求调用 Webhook？

**解决方案**：
1. 代码平台本身提供了 Token 验证机制
2. 可以在服务端验证请求签名
3. 实现了基础的防爬虫机制

### 难点 4: 异步处理可靠性

**问题**：异步处理过程中如何保证可靠性？

**解决方案**：
1. 使用 Spring 的 `@Async` 注解
2. 捕获所有异常，记录日志
3. 数据库持久化，防止丢失
4. 重试机制（可扩展）

### 难点 5: 多数据库支持

**问题**：如何支持 SQLite 和 MySQL 两种数据库？

**解决方案**：
1. 使用 Spring Data JPA，屏蔽数据库差异
2. 通过 `@Value` 注入不同数据库的配置
3. 在配置文件中通过条件判断选择数据库驱动
4. 数据库方言自动适配

智能代码审查系统是一个将 AI 技术应用到代码审查场景的尝试，通过 AI 的力量提高代码质量，减少 Bug，提高开发效率。

这个项目能够让大家深刻体会到：

4. **完善的文档**能降低维护成本
5. **良好的监控**能快速定位问题
