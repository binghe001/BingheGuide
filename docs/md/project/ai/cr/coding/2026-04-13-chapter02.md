## 二、为什么要设计一个独立的客户端层

在实际开发中，我们可能会因为成本、速度、稳定性等原因切换不同的模型。比如：
- 日常开发用 DeepSeek（便宜，够用）
- 核心模块用 GPT-4（更准确）
- 国内部署用通义千问或 GLM（合规）

如果代码里到处是 `new OpenAIClient(...)`，换模型时得改十几个文件，太痛苦。所以我们做了一层抽象：

- **统一接口** `LLMClient`：不管底层是谁，上层只需要调用 `completions(messages)` 拿结果。
- **工厂模式** `LLMFactory`：根据配置文件 `llm.provider` 的值，自动给你返回对应的客户端实例。
- **模板方法** `BaseOpenAIClient`：把 HTTP 请求、超时、重试、JSON 解析等通用逻辑写在基类里，各个子类几乎不需要写代码（除了构造函数）。

这样一来，上层业务代码（比如 `CodeReviewService`）只需要注入 `LLMFactory`，然后 `llmFactory.getClient()` 就能拿到当前配置的客户端，完全不知道底层是谁。

## 四、LLM 客户端调用流程

先看一张时序图，理解一个完整的审查请求是如何从业务代码走到具体模型 API 的：

```mermaid
sequenceDiagram
    participant CodeReviewService as CodeReviewService
    participant LLMFactory as LLMFactory
    participant BaseClient as BaseOpenAIClient
    participant OkHttp as OkHttpClient
    participant LLM_API as LLM API

    Note over CodeReviewService,LLM_API: LLM客户端调用流程

    CodeReviewService->>LLMFactory: getClient()
    LLMFactory-->>CodeReviewService: 返回对应客户端实例

    CodeReviewService->>BaseClient: completions(messages)
    BaseClient->>BaseClient: 构建JSON请求体

    BaseClient->>OkHttp: POST请求到LLM API
    OkHttp->>LLM_API: 发送HTTP请求

    LLM_API-->>OkHttp: 返回JSON响应
    OkHttp-->>BaseClient: 返回Response

    BaseClient->>BaseClient: 解析JSON响应
    BaseClient-->>CodeReviewService: 返回文本内容
```

简单说就是：业务层拿到客户端 → 调用 `completions` → 基类负责拼 JSON、发请求、解析 → 返回纯文本。

## 六、BaseOpenAIClient 的请求构建细节

抽象基类里面做了哪些事？我画了张流程图：

```mermaid
flowchart TB
    Start[开始completions调用] --> BuildJSON[构建JSON请求体]
    BuildJSON --> CreateArray[创建messages数组]
    CreateArray --> LoopMessages{遍历messages}
    LoopMessages -->|有消息| AddMessage[添加message节点]
    AddMessage --> LoopMessages
    LoopMessages -->|无消息| SetModel[设置model字段]
    SetModel --> SetTemp[设置temperature=0.1]

    SetTemp --> BuildURL[构建请求URL]
    BuildURL --> CheckProvider{provider类型?}

    CheckProvider -->|glm| AddGLMPath[添加GLM路径]
    CheckProvider -->|其他| AddCommonPath[添加通用路径]

    AddGLMPath --> CreateBody[创建RequestBody]
    AddCommonPath --> CreateBody

    CreateBody --> CreateRequest[创建OkHttp Request]
    CreateRequest --> AddHeaders[添加Authorization和Content-Type头]

    AddHeaders --> LogRequest[记录请求日志]
    LogRequest --> Execute[执行HTTP请求]

    Execute --> CheckSuccess{响应是否成功?}
    CheckSuccess -->|否| HandleError[抛出异常]
    CheckSuccess -->|是| ParseResponse[解析JSON响应]

    ParseResponse --> ExtractContent[提取content字段]
    ExtractContent --> LogSuccess[记录成功日志]
    LogSuccess --> End[返回文本内容]

    HandleError --> LogError[记录错误日志]
    LogError --> End
```

其中有个小坑：智谱 GLM 的 chat 接口路径不是标准的 `/chat/completions`，而是 `/api/anthropic`，所以我们在 `CheckProvider` 那里特殊处理了一下。
